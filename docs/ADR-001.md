# ADR-001: abstention is a feature, not a failure mode

Status: accepted, 2026-10-13

## Context

Most RAG demos optimize for answer rate: every question gets an answer, and
the eval counts how many look right. In production, the cost of a confident
wrong answer (a wrong refund policy quoted to a customer) dwarfs the cost of
saying I don't know.

## Decision

The pipeline returns an explicit abstention when the best grounding score is
under 0.35 after one rewrite hop. The UI renders abstentions as a distinct,
designed state. Not an error, not an empty box.

Thresholds were set by hand on the 5 demo questions:

* 0.45: below this, a rewrite is worth one hop. Above it, answer directly.
* 0.35: below this after the rewrite, abstain.

## Consequences

Answer rate drops on adversarial questions by design. The eval table in the
README reports this instead of hiding it.

The thresholds are corpus-specific. A production port would tune them on a
labeled eval set and report precision and recall of the abstain decision
itself. When it answers, how often is it right matters more than how often
it answers.

The rewrite step is capped at one hop. Endless rewriting is its own failure
mode (latency, drift). The pipeline prefers a fast abstain over a slow
guess.
